## Implemented behavior and decision scope

- Correctly interprets mixed EU and US amount separators (`1.234,56` and `1,234.56`), ordinary/NBSP/narrow-NBSP grouped numbers, decimal comma, leading signs, Unicode minus, trailing minus and accounting parentheses. Rejects malformed groups, numeric prefixes followed by text, nonfinite values, conflicting Debit/Credit cells and ambiguous lone separators instead of inferring an amount.
- Validates real calendar days including leap years. Supports the existing explicit ISO and day/month/year forms and timestamp suffixes; removes permissive platform-dependent date fallback. Keeps the calendar date written by the bank rather than changing it through timezone conversion.
- Duplicate checking now includes transactions accepted earlier in the same upload. Existing records must match user, account and currency. Preserves the pre-existing amount tolerance (`0.005`) and reference/description comparison behavior.
- Malformed column counts, unclosed quoted lines, invalid dates and invalid/ambiguous amounts no longer disappear behind complete-success status. Mixed valid/invalid files retain valid transactions and set `needs_review`; files without valid or duplicate transactions remain `failed`. `StatementImport.errorMessage` records row-specific warnings using original physical line numbers.
- Integration follow-up: quote state persists across physical lines. Every continuation of an unsupported multiline field (including an apparently valid bank row, escaped quotes or a blank physical line) is withheld through its closing quote. An unclosed field withholds the remainder of the file, preventing quoted text from becoming fabricated transactions.
- Parser outcomes add optional `rejectedRows` carrying original line text, parsed raw fields, physical row number and reason. Existing input shape is unchanged.
- Malformed running balances generate warnings. If the newest dated balance is invalid, an older balance is not passed off as the latest closing balance.

This is input-validation/remediation under existing PI provenance and data-quality requirements (SPEC workflow steps 1–2, D-010). It does not create new financial formulas, actions, matching tolerances, empirical claims or policy thresholds. Reconciliation classification and transfer matching were untouched.

## Limitations and unresolved interpretation

- `1,234` / `1.234` can mean either a grouped integer or a three-decimal number. Without bank/locale metadata the parser withholds that row and requests review; it does not silently choose. Supported multiple grouping separators (`1,234,567`) and mixed decimal/grouping separators are unambiguous.
- Raw rejected rows are retained in the returned parser outcome, but existing callers do not yet persist that optional collection or offer row correction/reimport UI. Statement-level warning text persists through the existing StatementImport field.
- Proper quoted multiline CSV fields remain unsupported; the opening, continuation and closing physical lines are flagged and preserved for review rather than imported. Independent records resume only after the closing quote. If it never closes, no subsequent physical line is treated as a new transaction.
- Day/month/year continues to mean day-first as in the original parser; no US month-first inference was added. Unsupported textual date forms now require review instead of platform-dependent interpretation.
- Duplicate matching retains the existing approximate amount comparison and conditional reference matching. Legitimate indistinguishable repeated transactions remain a limitation of those existing semantics; no new matching policy was invented.
