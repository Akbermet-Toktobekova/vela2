## Implementation and decisions
D-012/D-013: independent beta document namespace on SQLite; AES-256-GCM encrypted JSON with per-user/document AAD; key-verification metadata; Windows CurrentUser DPAPI protects a generated random 32-byte persistent key alongside the database. A provided explicit 32-byte key is supported. In-memory tests may generate an ephemeral key. Persistent operation outside Windows requires an explicit key. Missing, corrupted or incorrect keys never cause database reset or plaintext fallback. No changes to the legacy prototype database or shared financial formulas/policies.

Public API follows BETA-CONTRACT.md: constructor {filename?,key?}, database, get, put, remove, deleteUser, close, backup. Coordinator-requested encryptText/decryptText helpers support encrypted auth fields. deleteUser removes beta_documents only: caller must delete auth/job index records separately. Document JSON is encrypted; SQL namespace identifiers and table metadata are not.

Backup uses SQLite VACUUM INTO for a consistent committed snapshot, including tables owned by auth, and refuses existing destination files. For DPAPI mode it copies the protected key sidecar beside the backup. Restoring on the same Windows account/machine is verified. Moving to another Windows identity/machine requires a separately designed secure key-transfer process; copying the DPAPI blob does not guarantee cross-machine portability. Explicit-key backups require the original key on restoration. No raw key is printed or put in process arguments. PowerShell DPAPI data travels through stdin with diagnostic output suppressed.
